Un Solo Cocinero, Cientos de Clientes

Analogía

Imaginá un restaurante muy popular con un solo cocinero (JavaScript) y cientos de clientes (tareas) esperando sus pedidos.

  • Si el cocinero tuviera que esperar a que el horno termine una pizza antes de cortar los vegetales del siguiente plato, el restaurante colapsaría.
  • JavaScript es single threaded (un solo hilo): solo puede ejecutar UNA instrucción a la vez.
  • ¿Cómo hace para cargar un video, escuchar tus clics y enviar un formulario "al mismo tiempo"? Ahí entra el Event Loop.

El Call Stack: La Pila de Ejecución

LIFO

Es la lista de tareas mental del cocinero: una estructura LIFO (Last In, First Out).

  • Al llamar a una función, se pone en la parte superior de la pila.
  • Cuando la función termina, se saca de la pila.
function saludar() { console.log("Hola") } function iniciar() { saludar() } iniciar() // iniciar() entra -> saludar() entra encima -> se ejecuta // -> saludar() sale -> iniciar() sale

Call Stack en Acción: ¿Qué Sale Primero?

Ejemplo

Aunque el delay del setTimeout es 0, "Async Action" sale ÚLTIMO.

  • El Event Loop espera a que el Call Stack esté completamente vacío antes de sacar algo de la cola.
function firstFunction() { console.log("First") } function secondFunction() { console.log("Second") setTimeout(() => console.log("Async Action"), 0) console.log("Third") } firstFunction() secondFunction() // Salida: First, Second, Third, Async Action

Síncrono vs. Asíncrono

Código Síncrono

Es secuencial: "hago esto, y hasta que no termine, no paso a lo siguiente". Predecible, pero peligroso si la tarea es pesada.

Código Asíncrono

Es delegable: "empiezo esto, pero como sé que va a tardar, te aviso cuando termine. Mientras tanto, sigo con otra cosa".

El Event Loop y la Task Queue

Dónde Encajan las Piezas

El Event Loop vigila constantemente dos cosas.

  • El Call Stack: ¿está vacío?
  • La Task Queue (cola de tareas): ¿hay algún aviso de que una tarea asíncrona terminó?
  • Si el Call Stack está vacío y hay algo esperando en la cola, el Event Loop lo toma y lo pone en el stack para ejecutarse.

Bloqueante vs. No Bloqueante

Bloqueante

Una operación que impide que el hilo principal continúe hasta completarse. Ej: un for de 10 billones de iteraciones. El navegador se congela.

No Bloqueante

Una operación que inicia un proceso y deja que JavaScript siga con lo siguiente. La respuesta se procesa más tarde. Ojo: "asíncrono" no es lo mismo que "paralelo".

setTimeout vs. setInterval

Una Vez vs. Repetido

Dos herramientas muy usadas para crear retrasos, mensajes temporales o acciones automáticas.

  • setTimeout(): se ejecuta UNA sola vez, después del delay.
  • setInterval(): se repite cada "tiempo", indefinidamente.
setTimeout(() => { // código a ejecutar }, tiempo) setInterval(() => { // se repite cada "tiempo" }, tiempo)

¿Por Qué el 3 Sale Antes que el 2?

Ejemplo

setTimeout es no bloqueante: JavaScript delega la espera al navegador y sigue con el siguiente console.log.

console.log("1. Inicio del script") setTimeout(() => { console.log("2. Tarea asíncrona (2s después)") }, 2000) console.log("3. Fin del script") // 1. Inicio del script // 3. Fin del script // (pausa de 2 segundos) // 2. Tarea asíncrona

Extra: Detener un Intervalo con clearInterval

Bonus

setInterval() devuelve un id; clearInterval(id) lo usa para cancelar las repeticiones futuras.

const intervalId = setInterval(() => { console.log("Mensaje cada segundo") }, 1000) setTimeout(() => { clearInterval(intervalId) console.log("Intervalo detenido") }, 3500)

El Callback: "Llámame Cuando Termines"

La Forma Más Antigua

Un callback es simplemente una función que pasás como argumento a otra función.

  • Problema: si tenés muchas tareas seguidas (loguear → buscar perfil → cargar fotos), terminás con funciones dentro de funciones dentro de funciones.
  • A esto se lo conoce como Callback Hell (el infierno de los callbacks).
// Callback Hell loguear(usuario, () => { buscarPerfil(usuario, () => { cargarFotos(usuario, () => { console.log("listo... por fin") }) }) })

La Promesa: Un Objeto con Futuro

Pending

Hacés el pedido de la pizza. Tenés el ticket (el objeto Promesa), pero la pizza todavía no llegó.

Fulfilled

La pizza llega caliente. La promesa se resolvió con éxito.

Rejected

Llaman para decir que no hay ingredientes. La promesa falló por un error.

Sintaxis: new Promise()

resolve / reject

¿Por qué usar Promesas en vez de Callbacks? Permiten código más limpio y manejo de errores centralizado, con .then() y .catch().

const miPromesa = new Promise((resolve, reject) => { const exito = true if (exito) { resolve("¡Todo salió bien!") // pasa a fulfilled } else { reject("Algo falló") // pasa a rejected } })

Explorando el Método .then()

Esperar el Resultado

.then() "espera" a que la promesa se resuelva, sin bloquear el resto del código mientras tanto.

function obtenerUsuario() { return new Promise((resolve) => { setTimeout(() => { resolve('Usuario cargado') }, 3000) }) } obtenerUsuario().then((respuesta) => { console.log(respuesta) }) // Después de 3 segundos: "Usuario cargado"

El Problema: ¿Por Qué Async/Await?

Encadenar .then()

Imaginá que necesitás: validar un usuario → obtener sus publicaciones → cargar los comentarios.

  • Con .then(), terminás con una cadena larga de promesas anidadas.
  • Async/Await te deja "esperar" a que una promesa termine antes de pasar a la siguiente línea, sin bloquear el resto de la app.

Las Palabras Clave: async y await

Sintaxis Core

Una función async siempre devuelve una Promesa, incluso si devolvés un simple texto.

  • await pausa la ejecución de ESA función hasta que la promesa se resuelva, y devuelve el valor.
  • await solo funciona dentro de funciones marcadas con async.
async function saludar() { return "Hola Mundo" } const datos = await [ { id: 1, name: 'Juan Pérez' } ]

Manejo de Errores: try / catch / finally

try

Acá va el código "peligroso" que podría fallar, como una petición de red.

catch

Si la promesa es rechazada (rejected), el control pasa acá con el error resultante.

finally

(Opcional) Código que se ejecuta SIEMPRE, haya éxito o error. Ideal para ocultar un "Cargando...".

Ejemplo de Flujo con Manejo de Errores

Todo Junto

async, await y try/catch/finally trabajando en equipo.

async function obtenerUsuario() { try { console.log("Cargando...") const usuarios = await [ { id: 1, name: 'Juan Pérez' }, { id: 2, name: 'Ana García' } ] const usuario = usuarios[0] console.log(`Usuario encontrado: ${usuario.name}`) } catch (error) { console.error("Algo salió mal:", error.message) } finally { console.log("Intento de conexión terminado.") } }

Error Común: Olvidar el await

#FindTheBug

Si llamás a una función asíncrona SIN await, obtenés el objeto Promise pendiente, no los datos reales.

  • await es el que "abre el sobre" de la promesa para sacar el contenido.
async function obtenerUsuario() { return "Juan Pérez" } const resultado = obtenerUsuario() console.log(resultado) // ❌ Promise { <pending> } const resultadoOk = await obtenerUsuario() console.log(resultadoOk) // ✅ "Juan Pérez"
