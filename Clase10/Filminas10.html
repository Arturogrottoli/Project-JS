El Restaurante: La Anatomía de una Petición

Analogía

Imaginá que estás en un restaurante. Vos sos el cliente (el navegador), el mozo es la Fetch API, y la cocina es el servidor donde vive la base de datos.

  • No vas directamente a la cocina: le hacés el pedido al mozo (una petición HTTP), y esperás.
  • El mozo vuelve con una bandeja TAPADA: eso es el objeto Response, todavía no es "la comida".
  • "Destapar y servir" el plato es, en JavaScript, extraer los datos con .json().

¿Qué es fetch()?

De XMLHttpRequest a Fetch

Históricamente, pedir datos a un servidor desde JavaScript era complejo y tedioso, con una tecnología llamada XMLHttpRequest.

  • Los navegadores modernos introdujeron Fetch API: más sencilla, limpia y basada en Promesas.
  • fetch() pide información a una URL externa, de forma asíncrona.
  • El código no se detiene mientras espera la respuesta: sigue, y nos avisa cuando la info llegó.
// Anatomía básica de un fetch fetch("https://jsonplaceholder.typicode.com/users") .then(response => { // Acá llega la "bandeja" (el objeto Response) console.log(response) })

APIs Públicas: Con Qué Vamos a Practicar Hoy

¿Qué es una API?

Una API (Application Programming Interface) pública es un servidor que expone datos listos para consumir, a través de URLs documentadas llamadas "endpoints".

  • No hace falta programar tu propio backend: alcanza con conocer la URL base y sus endpoints.
  • Las APIs de práctica suelen ser gratuitas y no piden autenticación (API key) para hacer GET.
  • Su documentación te dice qué endpoints existen y qué forma tiene el JSON que devuelven.
// PokéAPI: toda la data de los juegos Pokémon fetch("https://pokeapi.co/api/v2/pokemon/pikachu") // Rick and Morty API: personajes, lugares y episodios fetch("https://rickandmortyapi.com/api/character/1") // Las dos son públicas, gratuitas y sin autenticación: // ideales para practicar fetch() sin crear un backend propio.

El Objeto Response: La "Bandeja" de Entrada

Antes de Leer los Datos

Si imprimís ese response en consola, no vas a ver la lista de usuarios de inmediato: vas a ver un objeto "contenedor".

  • response.ok: true/false. La forma más rápida de saber si la petición fue exitosa (200 a 299).
  • response.status: el código numérico (200 éxito, 404 no encontrado, 500 error del servidor).
  • response.headers: información adicional, como el tipo de contenido recibido.
fetch("https://jsonplaceholder.typicode.com/users") .then(response => console.log(response)) // Response { ok: true, status: 200, headers: ... } // El cuerpo de los datos todavía no está "servido"

Leyendo JSON con response.json()

Texto → Objeto

La mayoría de las APIs modernas envían la información en formato JSON: aunque se parece a un objeto de JS, en realidad es una cadena de texto larga con formato específico.

  • Para poder usar forEach, filter o acceder a propiedades, hay que convertir ese texto con .json().
  • Punto crucial: .json() TAMBIÉN devuelve una Promesa. Hace falta un segundo .then() (o un segundo await).

Ejemplo con Encadenamiento de Promesas

.then().then()

Encadenamos dos .then(): el primero convierte la Response en JSON, el segundo ya trabaja con los datos reales.

fetch("https://jsonplaceholder.typicode.com/users") .then(response => response.json()) // Paso 1: convertir la Response a JSON .then(data => { // Paso 2: usar los datos console.log(data) // acá sí, el array de usuarios })

Verificación de Éxito con response.ok

#FindTheBug

¿Qué pasa si escribís mal la URL o el servidor está caído? fetch() tiene un comportamiento particular.

  • fetch() solo se "rechaza" (va al .catch) si hay un error DE RED (te quedaste sin internet).
  • Si el servidor responde 404, fetch() lo trata como una respuesta VÁLIDA: no dispara el error solo.
  • Por eso hay que verificar response.ok nosotros mismos, antes de procesar los datos.

El Flujo Profesional: fetch() + Async/Await

La Sintaxis Recomendada

Es la sintaxis más moderna y recomendada, por su legibilidad: se lee de forma secuencial, como el resto del código.

async function obtenerUsuarios() { try { const response = await fetch("https://jsonplaceholder.typicode.com/users") // Verificamos si la respuesta fue exitosa if (!response.ok) { throw new Error(`Error en la petición: ${response.status}`) } const data = await response.json() console.log("Datos recibidos:", data) } catch (error) { console.error("Hubo un problema:", error.message) } } obtenerUsuarios()

Simulación desde un Archivo JSON Local

Misma Lógica, Otra Fuente

Este proceso se puede replicar simulando una base de datos local: en vez de la URL de una API, le pasamos a fetch() la ruta de un archivo .json propio.

Ideal para Proyectos Personales

Es un método muy útil para armar proyectos sin tener que crear una API propia con datos simulados: fetch("./data.json") funciona igual que contra un servidor real.

Errores Comunes y Mejores Prácticas

#FindTheBug

Olvidar el await en response.json() es, por lejos, el error más común de esta unidad.

  • Sin el segundo await, "data" es una Promesa pendiente, no los datos.
  • El JSON que viaja por internet es puro texto: no podés ejecutar funciones ni usar undefined ahí adentro.
// ❌ Error: falta el await en response.json() const response = await fetch(url) const data = response.json() // data es una Promesa pendiente, no los datos // ✅ Correcto const data = await response.json()

¿Qué es una Librería Externa?

Un Paquete de Soluciones

Imaginá que estás construyendo una tienda online: el usuario hace clic en "Eliminar producto" del carrito.

  • Opción 1: confirm() nativo, ese cuadro gris que parece un error del sistema.
  • Opción 2: un cuadro elegante, con iconos, colores de marca y animaciones suaves.
  • Una librería es código ya escrito por otros desarrolladores, listo para importar y resolver ese problema común.

Cómo Integrar Librerías: CDN vs. npm

A. Vía CDN

Agregás una etiqueta <script> en tu HTML que apunta a un servidor donde vive el código de la librería. Pros: configuración instantánea. Contras: dependés de tener internet mientras desarrollás.

B. Vía npm

Usás la terminal para descargar el código a tu carpeta local: npm install sweetalert2. Pros: el código vive en tu proyecto, más seguro y profesional. Contras: requiere algo más de configuración inicial.

SweetAlert2: Transformando las Alertas

Adiós, alert()

window.alert() cumple su función, pero tiene un gran problema: detiene la ejecución de TODO el navegador.

  • SweetAlert2 reemplaza esos mensajes con modales elegantes que no bloquean el hilo principal.
  • Totalmente personalizables: título, texto, ícono y color del botón.
// Swal es el objeto global que da la librería Swal.fire({ title: '¡Éxito!', text: 'El usuario se ha registrado correctamente', icon: 'success', confirmButtonText: 'Genial' })

El Poder de las Promesas en SweetAlert2

.then(result => ...)

Como vimos en la unidad de Asincronismo, SweetAlert2 usa Promesas: nos permite esperar a que el usuario tome una decisión.

  • result.isConfirmed es true solo si el usuario hizo clic en confirmar.
Swal.fire({ title: '¿Estás seguro?', text: "¡No podrás revertir esto!", icon: 'warning', showCancelButton: true, confirmButtonText: 'Sí, borrar' }).then((result) => { if (result.isConfirmed) { Swal.fire('¡Borrado!', 'Tu archivo fue eliminado.', 'success') } })

Toastify: Notificaciones No Intrusivas

Una Nota Adhesiva

A veces no queremos interrumpir al usuario con un cuadro en medio de la pantalla: solo avisarle algo chico, que desaparece solo.

  • Un Toast aparece en una esquina, da la información, y se va solo después de unos segundos.
Toastify({ text: "Producto añadido al carrito", duration: 3000, close: true, gravity: "top", position: "right", style: { background: "linear-gradient(to right, #00b09b, #96c93d)" } }).showToast()

SweetAlert2 vs. Toastify: ¿Cuándo Usar Cada Una?

SweetAlert2: Decisiones Críticas

Usalo cuando necesitás que el usuario CONFIRME algo antes de seguir: borrar un registro, confirmar una compra, cerrar sesión.

Toastify: Confirmaciones Informativas

Usalo para avisos que no necesitan ninguna acción del usuario: "se guardó", "se agregó al carrito", "conexión perdida".

Errores Comunes y Mejores Prácticas

La "Libreritis"

Muchos desarrolladores se emocionan e instalan 20 librerías para un proyecto pequeño: la app carga muy lento.

  • Regla de oro: antes de instalar, preguntate "¿puedo resolver esto con 5 líneas de JS puro?".
  • Olvidar el CSS: si instalás la librería pero ves un texto feo, seguro olvidaste importar su .css.
  • No leer la documentación: no intentes adivinar el nombre de una propiedad, andá a la página oficial.

Actividad Integradora

APIs, Peticiones y Librerías

Integrá fetch hacia una API y/o archivo JSON local, y sumá al menos una librería (SweetAlert2 o Toastify) para comunicarte con el usuario.

✓ Solicitar datos: al cargar la página, traer info desde la api y/o el JSON local

Sin API propia: sirven Fake Store API, JSONPlaceholder o PokeAPI. Entregable: repositorio de GitHub público con HTML y JS.
