Node.js: JavaScript sin Navegador

El Motor Debajo del Capó

Node.js utiliza el motor V8, el mismo componente ultrarrápido que usa Google Chrome para procesar JavaScript, sacado del navegador.

  • Antes de 2009, programar el servidor de una web requería otros lenguajes: PHP, Java o Ruby.
  • Node.js permitió usar un solo lenguaje (JavaScript) para todo el proyecto: frontend y backend.
  • Le añade "superpoderes" para interactuar directamente con el sistema operativo de tu computadora.

Diferencia Clave entre Entornos

En el Navegador

Tenés acceso al objeto window y document. Podés cambiar el color de un botón o detectar un scroll. No podés leer archivos del disco duro del usuario, por seguridad.

En Node.js

No existe el DOM ni el document, porque no hay una "página" que mostrar. En su lugar, tenés acceso al sistema de archivos (fs), a la red y a procesos de la computadora.

Casos de Uso de Node.js

Servidores Web (Backend)

Es el uso más famoso. Node.js es excelente para aplicaciones que necesitan manejar muchas conexiones al mismo tiempo, como un chat en tiempo real o una red social. Netflix lo usa para gran parte de su backend.

Scripts de Automatización

Imaginá que tenés 1.000 imágenes que necesitás renombrar o cambiar de tamaño. En vez de hacerlo a mano, escribís un pequeño script de JavaScript y lo ejecutás con Node.js para que haga el trabajo pesado en segundos.

Errores Comunes y Mejores Prácticas

La "Caja Negra"

Nunca toques la carpeta node_modules directamente: es generada automáticamente por npm y tus cambios desaparecerán.

  • "Estoy aprendiendo Node" es un error común: Node no es un lenguaje nuevo, es JavaScript con otras APIs disponibles.
  • package.json es el "documento de identidad" de tu proyecto: leelo siempre, ahí ves librerías y comandos disponibles.
// NUNCA edites archivos dentro de esta carpeta node_modules/ // Este es tu mapa: leelo siempre package.json // dependencias y scripts del proyecto

El Problema de Escalar con JS Manual

Enfoque Imperativo

Con document.querySelector y manipulación manual, le das al navegador instrucciones paso a paso de cómo cambiar la interfaz.

  • Sincronización: si un dato aparece en dos lugares, hay que acordarse de actualizar ambos manualmente.
  • Complejidad: rastrear qué código cambió qué parte del HTML es una tarea detectivesca.
  • Fragilidad: cambiar una clase en el HTML puede romper los selectores de JS silenciosamente.
// Agregar una tarea a mano, paso a paso const li = document.createElement('li') li.textContent = input.value lista.appendChild(li) // Los frameworks proponen otro camino: // enfoque Declarativo → decís QUÉ ver, // según los datos que tenés

Componentes: La Unidad Reutilizable

Como Piezas de LEGO

En vez de un único documento HTML gigante, la interfaz se arma con piezas independientes y reutilizables: los componentes.

  • Un componente encapsula Estructura (HTML), Lógica (JS) y Estilo (CSS) a la vez.
  • Cambiás el componente una sola vez, y se actualiza automáticamente donde sea que se use.

Ejemplo: Tarjeta de Producto

Imagen, título, precio y botón "Comprar". En Vanilla JS copiás y pegás ese HTML muchas veces. En un framework, lo definís una vez y lo invocás pasando distintos datos: nombre, precio, foto.

Estado y Reactividad: El Motor de la Interfaz

Interfaz = Framework(Estado)

El Estado son los datos que definen lo que se ve en pantalla: ¿está el modal abierto? ¿qué hay en el carrito?

  • Cuando el Estado cambia, el framework detecta ese cambio y actualiza la interfaz automáticamente.
  • Ya no tocás el DOM directamente: solo actualizás los datos, y el framework hace el trabajo sucio.
// Vanilla JS: hay que tocar el DOM a mano contador++ document.querySelector('#num').innerText = contador // Framework: solo actualizás el estado // y la interfaz se refresca sola setContador(contador + 1)

React: La Biblioteca Flexible

Meta (Facebook)

Oficialmente se define como una "biblioteca" y no un framework, porque solo se encarga de la vista (los componentes).

  • Filosofía "Todo es JavaScript": usa JSX, una sintaxis parecida a HTML dentro de funciones de JS.
  • Punto fuerte: ecosistema gigantesco, con librerías para casi cualquier necesidad.
  • Ideal para: proyectos donde querés elegir tus propias herramientas y la flexibilidad es clave.

La tecnología más popular actualmente

Vue: El Framework Progresivo

Evan You

Nació con el objetivo de tomar lo mejor de Angular y React para hacerlo más sencillo. Curva de aprendizaje muy suave.

  • Filosofía: separación de preocupaciones. Un componente tiene tres secciones claras: <template>, <script> y <style>.
  • Punto fuerte: documentación excelente y facilidad para integrarse gradualmente en proyectos existentes.
  • Ideal para: equipos que quieren empezar rápido sin sacrificar potencia.

Lo mejor de dos mundos, con simplicidad

Angular: El Framework Robusto

Google

Es un framework "con todo incluido": da todas las herramientas para routing, formularios y peticiones HTTP desde el primer segundo.

  • Filosofía: estructura y escalabilidad profesional. Usa TypeScript obligatoriamente.
  • Punto fuerte: consistencia. Un proyecto de Angular siempre tiene una estructura muy similar.
  • Ideal para: aplicaciones empresariales de gran escala, donde la estabilidad es clave.

Reglas estrictas para equipos grandes

¿Cuándo Usar un Framework?

Usá un Framework si...

Tu aplicación tiene muchos datos que cambian constantemente (dashboards, redes sociales), necesitás reutilizar muchas partes de la interfaz, el equipo va a crecer, o querés una SPA con navegación instantánea.

Usá Vanilla JS si...

Es una página estática (blog simple, landing page), necesitás un rendimiento extremo donde cada kilobyte importa, o es un script pequeño para una funcionalidad específica. No caigas en la sobreingeniería.

Requisitos: Estructura de Archivos

El Esqueleto del Proyecto

Un proyecto prolijo empieza por una estructura de carpetas clara y ordenada.

  • index.html en la raíz, como único archivo suelto: el resto va en carpetas organizadas.
  • Carpeta assets/ con recursos multimedia.
  • Al menos un archivo .json usado como base de datos simulada.
mi-proyecto/ ├── index.html ├── assets/ │ └── img/ ├── js/ │ ├── app.js │ └── ui.js ├── data/ │ └── productos.json └── styles.css

Requisitos: DOM e Interacción

Prohibido

Toda interacción con el usuario debe ser a través de la interfaz, nunca con cuadros de diálogo nativos.

  • Nada de prompt, alert ni confirm en ninguna parte del código.
  • Manipulación dinámica del DOM en respuesta a las acciones del usuario.
// MAL: cuadros de diálogo nativos const nombre = prompt("¿Tu nombre?") alert("Producto agregado") // BIEN: interfaz propia + librería externa Toastify({ text: "Producto agregado" }).showToast()

Requisitos: Arrays, JSON y Funciones de Orden Superior

Datos Reales, no Hardcodeados

Ningún array de objetos vive directamente en el .js: todos deben estar en un .json y consumirse con fetch.

  • Se usan al menos 2 funciones de orden superior distintas: map, filter, reduce, find, some, forEach.
  • Se usan para buscar, filtrar, transformar o calcular datos del simulador.
const productos = /* desde productos.json */ const disponibles = productos.filter(p => p.stock > 0) const total = carrito.reduce( (acc, item) => acc + item.precio, 0 )

Requisitos: Storage y Operadores Avanzados

Persistencia y Sintaxis Moderna

El proyecto debe implementar localStorage o sessionStorage con las cuatro operaciones básicas.

  • Guardar, modificar, borrar y vaciar el storage, para una experiencia de usuario correcta.
  • Código con al menos: operador ternario, operador OR (||) y destructuring.
const carrito = JSON.parse(localStorage.getItem('carrito')) || [] const { nombre, precio } = producto carrito.length === 0 ? mostrarMensajeVacio() : renderizarCarrito(carrito)

Requisitos: Asincronismo

fetch + async/await

El proyecto debe consumir la api/json local con la sintaxis moderna y un manejo de errores correcto.

  • try/catch/finally cuando aplique.
  • La app debe manejar errores de carga de datos, no romperse en silencio.
async function obtenerProductos() { try { const response = await fetch('data/productos.json') if (!response.ok) throw new Error('Error al cargar') const productos = await response.json() renderizarProductos(productos) } catch (error) { mostrarError(error.message) } finally { ocultarSpinner() } }

Requisitos: Librería Externa

Reemplazá lo Nativo

Debés incluir al menos una librería JS externa (SweetAlert2, Toastify u otra) y eliminar el uso de prompt, alert y confirm del navegador.

Mejor Experiencia de Usuario

En vez de un cuadro gris nativo, mostrás un diálogo elegante con íconos, colores de tu marca y animaciones suaves. Así como no fabricás tus propios ladrillos, usás librerías para resolver problemas comunes.

Requisitos: Lógica del Simulador

Circuito Completo, de Punta a Punta

El circuito principal debe estar completo: no alcanza con una parte del flujo.

  • Ejemplo e-commerce: ver productos → seleccionar → carrito → modificar cantidades → calcular total → confirmar.
  • Sin registro ni login: eso no es parte del alcance del proyecto.

No hay entrega parcial

Un carrito sin confirmación final, o un circuito incompleto, no cumple con la consigna del proyecto final.

Qué Evitar y Código Limpio

Qué Evitar

prompt, alert o confirm nativos; arrays de objetos hardcodeados en el .js; circuito del simulador incompleto; más de 3 archivos .js; archivos sueltos fuera de la raíz salvo index.html.

Código Claro

Nombres de variables, funciones y objetos semánticos (nada de x, a, funcA). Sin código comentado en desuso ni console.log innecesarios.
